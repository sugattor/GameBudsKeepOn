# 技術メモ

README は取扱説明書。ここには実装の理由と実測の記録を置く。
道具を使うだけなら読む必要はない。

## 1. 用語

| 用語 | 意味 |
|---|---|
| Engine | SteelSeries GG が開くローカルの HTTPS API |
| HID | USB の Human Interface Device。ドングルと直接やり取りする経路 |
| レポート | HID で送受信する決まった長さのバイト列 |
| 実行 | 接続の確認から書き込みまでを 1 回通すこと |

## 2. 経路の選び方

既定は `Auto`。GG が動いていて API が見つかれば Engine、それ以外は HID。

| 状況 | 選ばれる経路 |
|---|---|
| GG が起動していて、API が見つかる | Engine |
| GG が起動していない | Hid |
| GG が起動しているが、API が見つからない | Hid |
| ドングルが USB に見えない | どちらもうまくいかない |

GG のポートは起動ごとに変わる。番号を決め打ちしない。
SteelSeries のプロセスの待ち受けを順に試し、`/v1/connectedDevices` が JSON で返るものを API とする。
証明書は自己署名なので検証を無効にする。`Origin` ヘッダが要る。

Engine の経路は GG が動いているときだけ選ばれる。
GG の手元の値も同時に直すので、GG と取り合いにならない。
HID の経路は GG が要らない。

GG の有無で、ケースから出したあとに戻る値が違う。

| 状況 | 戻る値 | 出所 |
|---|---|---|
| GG が動いている | 10 分 | ユーザーの報告と掲示板の報告 |
| GG を閉じている | 0 分（なし） | この PC での実測 |

GG が動いているときの 10 分は、この PC では測れていない。
GG の手元のコピーが古いまま残る弱点があるため、Engine の経路も残している。

## 3. Engine の呼び出し順

| 順番 | メソッドと URL | 目的 |
|---|---|---|
| 1 | `GET /v1/connectedDevices` | ドングルが接続中か確認する |
| 2 | `POST /device/<ID>/function/get_fw_version` | イヤホン本体が生きているか、直接問い合わせる |
| 3 | `GET /device/<ID>/configurations` | 現在の設定を読む |
| 4 | `PUT /configuration/<ID>` | `inactivity_timer.minutes` だけ書き換える |
| 5 | `POST /configuration/<ID>/forceDeploy` | 有効化が外れていれば戻す |
| 6 | `GET /device/<ID>/configurations` | 読み直して確かめる |

`settings` には JSON を文字列にしたものを入れる。オブジェクトのまま渡すと通らない。
読み直した現在の設定をそのまま送り返し、13 のキーのうち目的の 1 つだけを変える。
残りの 12 を送らないと、他の項目が既定へ戻る。

`PUT` の直後に `active` が 0 に外れることがある。`forceDeploy` で戻す。
本体への書き込み自体には `forceDeploy` は要らない。

接続の確認は `get_fw_version` を使う。返ってくる文字列の 5 番目に、イヤホンのファームウェアのバージョンが入る。
`GET /device/<ID>` の `firmware.version` は Engine の手元のコピーで、しまっても接続済みのまま。
これを使うと、しまう・取り出すの切替を検出できない。

| 状況 | 動作 |
|---|---|
| 接続できている | 現在と同じ値でも毎回書き込む |
| イヤホンが未接続・ドングル無し | 書き込まない |

GG を使わない PC で、イヤホンが約 10 分で切れる事象が 2 回起きた(2026-11-25)。1 回目は目標 0 で書き込みなし(当時のコードは一致時スキップ)。2 回目は実行したが切れた。
同じ PC で、240 を書いてから 0 にしたら 1 時間以上切れなかった(2026-11-25)。0(なし)そのものが約 10 分扱いになるわけではないと分かった。残る疑いは「イヤホン本体は値が変化する書き込みだけ取り込み、同じ値の書き込みは無視する」。これなら 0=0 の再書き込みは本体に届かない。このため実行は常に、中間の大きい値(240。目標が 240 のときだけ 241)を書いてから目標を書く形にした。中間の値を大きくしたのは、目標の書き込みが途中で失敗しても自動電源オフがほとんど効かない側に残るため。

### 踏んだ穴

| やったこと | 実際の結果 |
|---|---|
| `POST /configuration/liveDeploy` | 成功を示す空の応答を返すが、何も変わらない |
| `POST /configuration` | 更新ではなく新規作成になる。設定が増える |
| `POST /configuration/<ID>/deploy` | エラーになる |
| `POST /configuration/<ID>/forceDeploy` | 成功する。`active` が 1 に戻る |
| 関数の呼び出しに本文を付けない | 400 が返る |
| `Content-Type: application/json; charset=utf-8` | 関数の呼び出しでは弾かれる。`application/json` ぴったりが要る |
| 関数に存在しない名前を渡す | HTTP は 200。本文が error を含む |
| 起動ごとに変わるポートを決め打ちする | ポートがずれた日は黙って失敗し続ける |

`last_deployed` が 1 になることは確認済み。
USB のパケットは USBPcap で採取して確認した。
ドングルから出る電波そのものは観測していない。

## 4. HID のデータ形式

ドングルは複数の HID チャネルを出す。命令を受け付けるのは `MI_03`。Audio の `MI_04` と `MI_05` は使わない。
探すときは `vid_1038&pid_230a` と `mi_03` だけを見て、インスタンス名は見ない。
差し直しは確認済み。別の USB ポートへ移した場合は未確認。

ハンドルは読み書き両方、共有ありで開く。重複読み取りを使うので `FILE_FLAG_OVERLAPPED` を付ける。

### 状態の返事の読み方

`b0 00` を送ると 65 バイトの返事が来る。
先頭はレポート ID 0 なので、位置は `b0` を 1 番目として数えると 1 つ後ろへずれる。

| 位置 | 意味 | 実測 |
|---|---|---|
| 1 番目 | 送った命令と同じ値 | `b0` |
| 4 番目と 5 番目 | イヤホンの左右の状態 | `03 03` は取り出して接続。`02 03` はケースへ入った瞬間 |
| 6 番目と 7 番目 | 電池。1 番目が左、2 番目が右(GG の画面と照合) | `58 59` は左 88% と右 89% |
| 12 番目 | 自動電源オフの分数 | `2d` は 45 分。`00` はなし |

状態を読むときは、先にキューを空にしてから `b0 00` を送る。
受け取りのバッファは 513 バイト要る。64 バイトだと、装置が送る 512 バイトのレポートが収まらず何も返らない。

### 書き込み

`c1 <分数>` を 2 回送る。GG も同じ命令を 2 回送る。
ハンドルを開いたままにせず、使い終わったら閉じる。

| 送った値 | レポートの並び | 読み戻した値 |
|---|---|---|
| 30 分 | `c1 1e` | 30 分 |
| 45 分 | `c1 2d` | 45 分 |
| 15 分 | `c1 0f` | 15 分 |
| 0 分 | `c1 00` | なし |

### 実測で分かった制約

| 試したこと | 結果 |
|---|---|
| 新しいプロセスで 11 秒ごとに 6 回読む | 6 回とも返事が来た |
| 同じプロセスで 4 回読む | 1 回目だけ。残りは時間切れ |
| 同じプロセスでハンドルを開き直して読む | やはり 1 回目だけ |
| 読み取りを先に待たせてから書く | 書き込みが送られない |
| 書き込みを 10 本続けて送る | 10 本すべて USB に出た |
| 同じプロセスで中間値 240 と目標値を続けて送る | 次の実行の変更前に最後の目標値が載った(2026-11-25 実測)。同じプロセスの連続送信は最後の値が効く |
| GG 起動中に共有ハンドルで読む | 間違って返事を GG に先取りされることがある(電池が読めず、接続がいいえになる)。同じプロセスで取り消さず送り直しても次の実行まで回復しない(実測)。新しいプロセスで 1 回読むと取れるので、アプリは読み取りが失敗したときだけ新プロセスで 1 回だけ状態を読み直している |

だから読み取りは、1 回の実行につき 1 回だけ。
書き換えたか確かめるには、もう 1 回実行する。
実行は 45 秒を過ぎると外から強制終了される。詰まったまま残らない。

イヤホンが使われていない間に書き込むと、PC 側だけ変わる。

| 条件 | 結果 |
|---|---|
| 使っている間に 1 分を書いた | 1 分ほどで切れた。値どおり |
| 使われていない間に 90 分を書いた | PC 側は 90 分。本体は 1 分のまま |
| 使っている間に 45 分を書いた | 出し入れを 3 回越えて 20 分以上切れなかった |

## 5. USB パケットの観測

USBPcap で USB の実際の動きを採取して確かめた。

| 送ったもの | USB に乗った並び | 装置の返事 |
|---|---|---|
| `b0 00` | `SET_REPORT` `bmRequestType=0x21 bRequest=9 wValue=0x0200 wIndex=3 wLength=64` | 4 ms 後に端点 `0x81` へ `b0 ...` |
| `c1 2d` | 同じ形。本文の先頭が `c1 2d` | 4 ms 後に `c1 00 ...` |

`c1` の 1 本だけで効いた。GG が送る 19 本の並びは要らない。
GG は同じ命令を 2 回送る。アプリも 2 回送る形にした。

未解決の点:

- GG の 19 本の並びが、イヤホンとドングルのどちらに保存されるか。
- ケースの出し入れで値が戻る仕組み。
- 同じプロセスで 2 回目以降の読み取りが失敗する理由。
- ドングルから出る電波そのもの。
- GG 無しの PC で 0(なし)にしてから約 10 分で切れる。中間の値を経由してから 0 にすると切れなくなった(2026-11-25)。本体は値が変化する書き込みだけ取り込む疑い。同じ値だけを書いたときにいつまで効いたかが復元できるか。

## 7. その他の実測

- GG を閉じてケースの出し入れをすると、保存済みの「なし」へ戻る。保存した値が残る場合の観測。
- 一度「なし」に保存していない初期状態は、メーカーの既定の 30 分のまま。
- GG の画面に無い 3 分を書くと、その値は本体でも効く。書いてから 181 秒後に未接続になった。

### PowerShell 5.1 で動かすための穴

5.1 と 7 のどちらも動く。踏んだ穴と塞ぎ方。

| 5.1 の挙動 | 塞ぎ方 |
|---|---|
| `Invoke-WebRequest` に `-SkipCertificateCheck` が無い | 7 では旗、5.1 では `ServicePointManager.CertificatePolicy` を実装した型で自己署名を許す |
| `ServerCertificateValidationCallback` に ScriptBlock を渡すと、.NET のスレッドから呼ばれたとき「実行空間が無い」で失敗(実測) | `ICertificatePolicy` を実装した型を Add-Type で作る |
| `Add-Type` の型を名前空間なしで宣言し、`Gamebud.` 付きで参照すると TypeNotFound(実測) | 宣言も `namespace Gamebud` で囲む |
| 既定の TLS に 1.2 が無い環境がある | `SecurityProtocol` に Tls12 を足す |
| PUT/POST が `Expect: 100-continue` を先に出し、Engine が応答しない | `Expect100Continue=$false` |
| `Invoke-WebRequest` の進捗バーの描画が遅い | `$ProgressPreference = 'SilentlyContinue'` |
| BOM の無い UTF-8 の日本語を読み間違える | スクリプトファイルを BOM 付き UTF-8 で保存する |

5.1 での実測(2026-11-23): Auto/Engine/Hid、読み取り、Engine 経由の書き込み(PUT+forceDeploy)、HID 経由の書き込みすべて成功。

### 切り時刻

音を出さずに置いたときの実測。

| 書いた値 | 結果 |
|---|---|
| 1 分 | 1 分ほどで切れた |
| 45 分 | 出し入れを 3 回越えて、20 分以上切れなかった |
| なし | 37 分以上切れなかった |

- この PC では、10 分で切れる事態は再現しなかった。
- ドングルを抜いて差し直しても、PC 側の値は保たれた。PC 側は接続時に初期化しない。
- 1 回の実行は 0.6 秒ほど。
